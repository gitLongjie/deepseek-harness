# Agent Note: 登录门在每次启动时重放存储的凭据对

Status: implemented

[English](2026-09-25-ui-login-launch-time-pair-replay.md) | 中文

## 问题

登录门此前信任 localStorage 快照。插件在启动时读取 `dsh.login.session`，只要上次登录存过资料，就用这份过期会话直接渲染应用——没有任何请求到达账号服务器。启动因此从未走登录流程：产品要求账号服务器在每次启动时重新签发 key，但被吊销或过期的 key 会被静默沿用。

同一生命周期上还附着第二个缺陷：侧边栏账号行的交互状态跨会话残留——打开退出登录下拉菜单、登出、再登录后，上一个会话的下拉菜单会重新出现。`SidebarAccount` 在登录门遮盖期间保持挂载，`menuOpen` 标志熬过了会话置空的间隙，portal 渲染的菜单就在重新登录后的应用上复活了。

## 决策

会话只存在于内存；持久化的事实是凭据对。`login()` 把 `{username, password}` 存到 `dsh.login.pair`，从不存储会话；`logout()` 在清除凭据引用的同时清除该凭据对，因此登出意味着重启之后仍保持登出。

`restore()`——由 `apply()` 在每次客户端启动时调用——读取凭据对，存在时走与手动登录完全相同的 `login()` 路径重放：同样的端点调用、凭据写入、网关目录同步与默认模型采纳。成功则不显示登录卡片直接进入应用；被拒绝则保留凭据对（下次启动重试），登录门显示卡片与失败原因——服务器消息原文，或网络/响应无法识别文案。重放进行中，`LoginGate` 只渲染不透明遮罩：卡片不会闪现，应用下层在认证完成前不可触及。

账号行在会话切换时关闭下拉菜单。`SidebarAccount` 在渲染期间检测会话身份变化并复位 `menuOpen`（props 变化时调整 state 的模式），为一个会话打开的菜单无法熬过登出→再登录周期，也不会有任何一帧画出过期菜单。

`response.text()` 移入 fetch 的 `try`，凭据对写入吞掉存储拒绝，使 `login()` 成为完整函数：启动重放不可能抛出未处理拒绝而把登录门卡死。

## 考虑过的替代方案

**继续恢复存储的会话，用会话端点校验存储的 `api_key`。** Deepagens Claw 部署只暴露一个认证线上方法 `POST /api/claw/login`；校验调用需要新增服务器路由，而且被校验的 key 正是存疑之物。重放凭据对复用既有契约，并在每次启动重新签发新 key。

**什么都不持久化，每次启动都显示卡片。** 满足"不用过期 key"的目标，但每次启动都要输入密码。凭据对重放是同一次线上调用、免掉手动步骤，且重放失败时卡片照样出现。

**用 `sessionStorage` 而非 `localStorage` 存凭据对。** Chromium 在异常退出后可能恢复 `sessionStorage`，"重启即登出"就不确定。产品要求是每次启动都重新认证。

**用会话上的 `useEffect` 复位下拉菜单。** effect 在绘制之后运行，重新登录后会留下一帧可见的过期菜单；渲染期复位在同一次提交中落定关闭状态。

**用会话作 key 重挂账号行**（`key={session.apiKey}`）。只有服务器签发不同 key 时才会复位状态；基于会话身份的渲染期复位无论服务器返回什么都成立。

## 后果

- 每次启动在界面定着前多一次登录往返；慢或挂起的账号服务器会让应用停在遮罩后（未配置超时——端点是部署方自有的服务地址）。
- 账号密码现在以明文存于渲染进程 profile 的 `localStorage`，与凭据层已经落盘的 API key 一致。只有手动登录和登出会写它，且本包只把它发往登录端点。
- 服务器侧改密码后，用户手动登录一次（更新存储的凭据对）之前，每次启动都会多一次失败的重放。
- `LoginState.status`（`idle`/`ready`）删除—— hydration 握手只为遮掩 localStorage 读取而存在；`restoring` 现在表达登录门必须隐藏的唯一阶段。

## 测试

聚焦测试固定了行为：凭据对解析容忍畸形值；新 store 为未登录；无凭据对时 `restore()` 为 no-op，有凭据对时经登录路径重放（端点请求体、凭据写入、目录同步），被拒绝时回退到卡片并显示服务器消息；会话永不落盘；登出清除凭据对。登录门在重放进行中只渲染遮罩、登录后不渲染任何内容。账号行用例打开下拉菜单、登出、再登录，并要求菜单保持关闭。
