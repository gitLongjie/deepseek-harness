# Agent Note: 客户端启动按进度排空 pending 链,而不是按固定窗口

Status: implemented

[English](2026-09-18-client-boot-progress-based-settle.md) | 中文

## 问题

渲染层的客户端启动在一个 8 个宏任务的排空窗口之后审计激活状态。等待中的 fiber 每个周期只下沉一层依赖,而客户端组合是一条深链——`ui-directory-picker-native` 等待 `slots` 与 `uiWorkspace`,它们的提供方又等待更下层的服务——于是在慢机器或冷启动上,8 个周期的预算在链排空之前耗尽,启动拒绝了一个只差一个周期就健康的树。同一个构建在构建机上每次都通过,这让失败看起来像一个它并不是的打包缺陷。

## 决策

排空循环改为按进度驱动:每一轮对 pending 与 loading 条目的集合及其状态做快照,静止(某轮快照无变化)按预算累计,预算为 128 轮静止——任何变化都会重置计数。循环在没有任何条目 pending 或 loading 时返回,或者在树静止满预算后返回;执行中的工作(`loading` fiber)属于集合成员,所以一个模块物化期间没有任何变化的轮次仍会让启动继续等待,直到静止是真实的。

## 备选方案

**把固定窗口调大(8 → 128)。** 否决:只是把一个魔法数换成另一个,仍然会输给任何比预算慢一层的机器;失败条件是"排空中静止",不是"静止了 N 轮"。

**去掉排空循环,`loader.await()` 之后立即审计。** 否决:这正是该循环修掉的回归——`loader.await()` 落定时,等待行距离重新激活只差一个周期,审计必须显式等出这次逐层重激活。

**改为监听 loader 事件而不是轮询。** 暂时否决:vendor 的 Loader 没有暴露"队列排空"事件,自己合成一个等于用额外状态复制这个 tick。若某台静止的机器真的耗穿了预算,再重审。

## 后果

真正无法满足的树(一个没人提供的服务)仍然会让启动失败,只是要经过约 128 轮静止而不是 8 轮;正在排空的树现在与机器速度无关地成功,因为决定权在进度而不在时钟。一个导入永久挂起的模块会让启动一直等待而不是失败;那种情形的权威仍然是 Loader 自己的导入错误。

## 验证

`packages/client/web/tests/boot-client.client.spec.ts` 钉住无人提供服务的失败报告(静止路径)和能排空链的激活报告;目标机器的失败只在构建机之外复现,本修改移除了它所依附的排空速度依赖。
