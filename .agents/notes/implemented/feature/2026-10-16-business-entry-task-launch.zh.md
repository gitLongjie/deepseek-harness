# Agent Note: 业务入口任务启动

Status: implemented

[English](2026-10-16-business-entry-task-launch.md) | 中文

## 问题

业务入口的七个条目（今日数据日报、今日选题、舆情速览、视频脚本、报告与汇报、一稿多形态、谣言识别与辟谣）只在分组的状态存储里记了一次点击，没有任何消费方：打开业务入口除了高亮该行之外什么都不发生。分组宣传了部署跑不起来的任务。

## 决策

点击条目现在打开它那个任务的对话。插件在 `slots`、`locale` 之外声明所需的 cordis 服务（`workspaces`、`sessions`、`uiWorkspace`）；模块表的 external 清单不变，因为启动流程不触及任何新模块。点击先找该条目已经拥有的会话——标题等于条目标签、未归档、最近更新的那个——并用 `uiWorkspace.openSession` 打开它，这就是全部效果：不新建会话，也不再发一遍指令。这个标题是条目自己的持久标记，由启动流程亲手写入，因此该关联能扛过刷新、重启，以及从未见过那次启动的窗口；用户离开的那个对话，就是这一行回去的地方。

条目还没有会话时，点击才启动一个。它按侧边栏「新会话」按钮同一套策略解析目标工作区——当前会话所在工作区，其次最近活跃工作区——并通过 `uiWorkspace.openWorkspace(id, beforeOpen)` 打开该工作区的新会话（新建或复用占位）。在同步的 `beforeOpen` 钩子里——新建会话在打开前即可寻址的既定时机——解析会话对象（先取 binding，再走 scope + `sessionOf`），把条目的本地化指令作为该会话的第一条用户消息发出（`session.prompt`，单个 text 分片，`queue` 模式），随后把会话重命名为条目标签（尽力而为：重命名被拒不把已送达的指令报成失败，而未命名的运行只是无法被找回）。没有任何已注册工作区时，点击直接 `sessions.create({})` 加 `openSession`，全新部署上任务照跑。

同一个标记还有第二个消费方：apply 级的一个快照存储发布 `{ current, entries }`——当前打开的是哪个会话，以及每个条目自己的历次运行（按时间倒序）——由会话列表与工作区归档集推导，两者任一变化即重新发布。它经保留的 `hooks` 通道以绑定好的 `useHistory` 选择器钩子抵达组件，因此行的展开列表与「回到哪个会话」读的是同一份快照，不会对「哪次运行最新」各执一词。行上显示历次运行的数量，展开后逐条列出（时间、进行中标记、当前标记），第一项就是新开一次。

Ctrl/⌘/Alt+点击就是显式的「新开一次」：跳过已拥有的会话另起一个。它绝不删除、替换或改名先前那个，行的悬浮提示把这两个手势写清楚。

启动状态挂在条目自己声明的存储上（`pending`、`error`、`historyFor`）：启动进行中各行禁用（转圈替代圆点），被拒的启动把自己的原因报在列表下方可点击关闭的提示里，而不是静默失败；展开状态也能扛过侧边栏收成窄栏。槽位的 inject 工厂拿到存储烘焙好的 actions，启动器因此能把结果报回发起的那一行。

每条指令都是多语言文案（`src/locales.js` 的 `prompt.<id>`，与行标签同放），而且是完整的指令而非表单：它先开口索要任务所需的输入——数据来源、监测对象、原始素材——因为点击本身什么都没带，然后再给出交付物的结构。`tests/launch.test.mjs` 用伪造的模块表和槽位注册表驱动构建产物：点击一行断言发出的指令与会话标题；断言第二次点击回到那次运行产出的会话而不是另起一个；断言同名会话取最新；断言已归档的被跳过；断言带修饰键的点击会新开且不碰已拥有的会话；断言某条目的历次运行按倒序发布、进行中的被标记、别的条目的运行不会混进来；断言展开列表渲染出这些运行、选中其一即打开它、当前打开的被标记、列表自己的入口能新开一次；以及无工作区的回退路径、被拒提示的产生、下一次启动会清除它；目录测试保证每个条目在两本词典里都有标签和指令。

## 备选方案

**每次点击都新开会话。** 否决：这些条目是常驻任务，普通点击若总是开一个新对话，上一个就得去工作区的会话列表里翻找——那一行回答的是「从头再来」，而这件事属于修饰键点击。

**把历次运行留给工作区的会话列表。** 否决：某个条目的历次运行是「一个任务的历史」，而那份列表把该工作区里每个任务、每段无关对话都混在一起。行上的展开列表是同一份数据、按条目收窄——这才是「不必知道标题也能找回上一次」的东西。

**种入输入框草稿而不是直接发送。** 否决：条目是任务入口，不是文本模板选择器。种入的草稿还要第二次操作才有事发生，而入口存在的意义就是启动任务。因此指令以对话方式索要输入，而不是携带待填占位符。

**把「条目 → 会话」的对应关系存在插件存储里（或宿主侧的注册表行里）。** 否决：任务会话的标题本身已经带着这个标记，它持久、扛得住插件重载与重启，也不需要第二份真相来源去在会话被删除、归档或手工改名时做对账。历史快照每次发布都从该标题推导，而不是另行存储。

**每个条目一条宿主侧斜杠命令。** 否决：命令面向已有会话的输入；条目的职责是创建并命名任务会话。注册命令会平添宿主面却不掌握导航，且这七个流程并不需要智能体缺少的宿主工具。

**每个条目一个专属主面板。** 否决：这些任务背后还没有数据面，面板只是无处提交的表单。指令优先的会话流程用智能体既有的工具（联网检索、文件生成）产出交付物，也为将来按任务生长专属界面留了空间而不动分组。

## 后果

任务已有会话之后，普通点击不再消耗模型轮次；只有启动一次运行时才消耗——那正是「立即开始」的代价。会话的自动标题再生成被条目标签的重命名固定，这同时也是条目能被找回、历次运行能被列出的原因。首次运行时占位新会话的草稿不受影响：指令走 `session.prompt` 而非 `setDraft`，发进同一个占位的未发送草稿得以保留。先前任何一次运行产出的东西都不会被后一次删除或隐藏：更早的会话在所属工作区的列表里、也在行的展开列表里保留自己的标题与历史；把其中一个归档，则下一次普通点击会新开一个任务而不是重新打开它。早先版本没写下标题的任务（重命名被拒的那次启动）既不会被列出也不会被找回——点击会另起一次运行，这与一个尚无任何会话的部署得到的答复相同。存储仍在刷新后重置（不变），目录仍是源码静态：新增任务要改 `entries.js` 加两本词典并重新构建。`apps/desktop/scripts/dev.ts` 每次 dev 启动都会重建并重新拷贝该插件到 web profile；打包安装器烘焙自己的副本，要把该行为随安装包分发需重新打包。
