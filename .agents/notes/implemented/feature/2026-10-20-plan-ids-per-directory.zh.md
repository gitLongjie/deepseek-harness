# Agent Note：计划 id 按输出目录编号

Status: implemented

[English](2026-10-20-plan-ids-per-directory.md) | 中文

## 问题

`video_plan` 从工具实例里的计数器分配 `vp-<n>`，而工具实例是按会话的，输出目录却是所有会话共用一个。于是第二个会话又从 `vp-1` 开始，`writePlan` 直接替换了第一个项目的计划文件。关键帧、片段、成片仍用旧名字躺在目录里，却不再被任何计划引用，工作台还会把新项目显示成"已渲染"。整个过程没有任何报错，数据就这么被替换了。

## 决定

编号序列跟着它命名的产物走：`allocatePlanId` 读取 `plans/vp-<n>.json` 的文件名，取最大编号，返回下一个空闲编号；本进程内已预留但尚未写盘的编号会被跳过，避免并发调用撞车。目录里没有计划时从 `vp-1` 起，所以单项目场景不受影响。

id 不做跨输出目录的全局唯一：两个指向不同目录的部署各自从 `vp-1` 开始是有意为之，因为编号只需在一个目录的产物之间唯一。

## 考虑过的替代方案

- **按会话给产物加命名空间**（`<sessionId>/plans/vp-1.json`）。否决：工作台、拼接路径、文件路由都投影同一个平铺目录，而会话 id 不是持久的项目身份——恢复或 fork 会话不会重命名任何东西，但 id 会变。
- **保留会话计数器，写盘时拒绝覆盖已存在的计划文件。** 否决：写盘时拒绝会丢掉模型刚编排好的计划，而重试仍然得重新编号。

## 后果

- 一个目录跨会话累积同一条编号序列。`vp-1` 永不复用，已完成项目的产物保持可寻址。
- 长期使用的目录编号会变大；序列不做压缩。

## 验证证据

- 同一进程内两个 agent、同一个输出目录：第二次 `video_plan` 返回 `vp-2`。
- 目录里存在 `plans/vp-7.json` 时，下一次分配返回 `vp-8`。
