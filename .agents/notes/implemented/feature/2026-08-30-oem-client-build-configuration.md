# Agent Note: OEM client build configuration

Status: implemented

English | [中文](2026-08-30-oem-client-build-configuration.zh.md)

## Problem

The browser product name, brand image, login endpoint, desktop update feed, localized login tagline, and time-specific blank-panel copy were owned by separate Vite, Electron, plugin, locale, and component files. An OEM build therefore required coordinated source edits and could compile artifacts with different identity or update destinations.

## Decision

The repository-root `oem.config.json` is the authored source for `productName`, `brandIcon`, `loginUrl`, `updateUrl`, the Chinese and English `loginTagline` values, and the five greeting slots in both languages. `brandIcon` names one root-relative `.ico` file under `apps/web/public`, and `updateUrl` names the HTTPS directory containing electron-updater channel metadata and release artifacts. `scripts/oem-config.ts` validates the exact field set, required strings, local ICO path, HTTPS endpoints, login taglines, and complete greeting dictionaries before projecting browser-owned values to `DSH_CLIENT_*` build values.

Vite and the dynamic client tsdown preset read the same validated file. Vite projects the configured name and icon into the initial document and the parsed Web App Manifest. The complete root build passes the projection through its existing client-build environment, so the build record continues to bind every public value to both artifact families. An explicitly supplied OEM `DSH_CLIENT_*` value wins over the file for one build; the empty login URL override retains the supported compile-out behavior.

The desktop development launcher rebuilds the client tsdown artifacts before Vite consumes them, so `pnpm run dev` reflects the current OEM file without a separate client build. Development and packaging copy the configured public ICO into the desktop application and tray icon slots before Electron consumes them. The renderer title bar reads the Vite-projected favicon link, the development executable embeds the synchronized application icon, and electron-builder packages that same icon. The launcher passes `productName` and `updateUrl` to the Electron main process. Desktop packaging generates an electron-builder overlay that carries the product name and update URL; the packaged main process reads those values from Electron's application name and packaged metadata. The updater configures a generic feed from `updateUrl` before its startup or manual check.

The Windows-only `test:update:local` command builds an explicitly versioned baseline and update into separate ignored directories without editing a manifest, validates the channel metadata and referenced files, reproduces publisher-safe artifact names when necessary, and serves the update directory with byte-range support on the loopback interface. The desktop deploy manifest explicitly supplies runtime-only Service Definition packages and the configured local IM plugin because development can resolve them from the workspace while electron-builder packages only the declared production dependency graph. Its private packaging environment replaces the inherited publisher with a generic loopback feed and writes an exact boolean rehearsal marker into packaged metadata. The runtime accepts HTTP only when that marker is present and the selected URL names `127.0.0.1`, `localhost`, or `[::1]`. Every other packaging path rejects non-HTTPS update URLs and passes `--publish never` unless the release command explicitly requests publication.

The framework-free desktop renderer owns a localized update control in a dedicated title-bar slot. The main process derives the generic metadata channel from the installed version's prerelease identifier, such as `local.yml` for `1.0.0-local.1`, and writes updater failures to the durable desktop log. It publishes checking, available, byte-progress, downloaded, installing, idle, and error states over the updater IPC channel. Startup checks report availability only through the title-bar control; explicit menu checks show a localized dialog for available, current, and failed outcomes. Confirming an available-version dialog starts the same progress-reporting download, while deferring preserves the title-bar action. Available updates also download directly from that control, and progress disables repeated actions and displays a clamped percentage. A downloaded package opens a localized restart prompt. Confirmation disables the control with installer-start feedback and asks the shared shutdown controller to dispose the application tree before electron-updater launches its visible native installer. Preparation waits for disposal at most once and returns at the five-second grace limit without exiting; the updater-triggered `before-quit` then bypasses the normal cleanup interception, so a timeout cannot leave NSIS racing another five-second shutdown. Deferral preserves the restart action, and the main process admits one install action per run. Failed checks expose retry, and a no-update result removes the control. The main process validates the closed check, download, and install action set before calling electron-updater.

The brand, login, boot-page, and Conversation packages consume only static property reads from that environment. Locale dictionaries remain the owners of product copy: the Conversation plugin replaces only its five typed greeting keys before registration, while the login plugin derives its localized page title from the configured product name and replaces its tagline with the configured locale value. The login card uses the same configured `brandIcon` as the other brand surfaces.

## Alternatives considered

**Import the JSON directly from each client package.** Rejected because dynamic plugin bundles and the Vite shell have different build graphs and publication roots. Direct imports would duplicate parsing and could place a repository-relative file outside a package's published closure.

**Serve runtime branding from the Host.** Rejected because the favicon, initial document title, and framework-free boot page must be correct before the client plugin tree connects. OEM identity is artifact content and changes only when the application is rebuilt.

**Keep individual environment variables as the primary interface.** Rejected because an OEM release would still require coordinating several build inputs. Environment variables remain narrow per-build overrides, while the versioned JSON file is the default source.

**Configure separate Web, application, and tray icon fields.** Rejected because independently authored files can drift while still producing a successful build. One ICO source is copied into each native slot and embedded directly in every Web consumer.

**Require a trusted local HTTPS certificate for update rehearsals.** Rejected because certificate creation and trust-store mutation add host state unrelated to updater behavior. The rehearsal binds an explicit HTTP exception to loopback hosts and an exact marker in packaged metadata; production configuration remains HTTPS-only.

## Consequences

One JSON edit updates the browser title and favicon, Web App Manifest, brand slots, login endpoint, update feed, mark and localized tagline, all time-specific Hero greetings, native desktop window and tray labels and icons, about copy, and packaged product identity in the same build. Invalid OEM fields stop the build before partial artifacts are produced. The configured brand icon must be a local `.ico` file under `apps/web/public`; remote and non-ICO images are rejected because Electron's Windows executable resource consumes ICO data. The update URL must use HTTPS and serve electron-updater metadata and matching artifacts. The configuration is public artifact content and must never contain credentials. Maintainers can exercise packaged update discovery, visible download progress, differential downloads, restart confirmation, and visible native installation locally without publishing a release or changing the authored version.
