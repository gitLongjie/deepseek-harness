# Agent Note: Sidebar business-entry group

Status: implemented

[English](2026-09-12-sidebar-business-entry-group.md) | 中文

## 问题

侧边栏的浏览区域只承载工作区浏览器和（可选的）知识库分区。当部署需要呈现自有任务条目——日报、速览、脚本、谣言识别——时，导航外壳中没有位置可以展示它们。把每个条目作为独立顶层 slot 会让外壳约定膨胀；把它们嵌入工作区浏览器则会把会话管理与部署专属的任务路由混为一谈。

## 决策

侧边栏外壳在浏览区域的 `sidebar.knowledge` 与 `sidebar.workspaces` 之间声明一个 `sidebar.business` 洞，沿用 `sidebar.knowledge` 的模式。独立的部署插件 `@xmanrui/dsh-business-entry`（源码位于 `business-entry/`，由其自带的 esbuild 脚本打包）填充它：一个可折叠的披露行，覆盖七个条目的静态目录（`dailyReport`、`topics`、`sentiment`、`videoScript`、`report`、`multiFormat`、`rumor`）。该分组的展开状态与用户的选择由条目声明的 store 承载，该 store 在外壳于折叠落定时卸载宽内容后仍然存活。由于没有宿主数据需要到达一个只记录选择的菜单，因此不声明注入面。在 56px 轨道中，该分组渲染单个图标按钮，请求外壳展开栏并同时打开分组。

条目目录位于插件的 `src/client/entries.ts`，并从数组字面量派生选择 id 类型，因此行的 id 与其标签不会分离。标签由 `business` 本地化命名空间承载。选择只是查看状态：目前没有页面、命令或会话动作消费该选择；未来的业务界面在发布时会读取同一个 store。

## 考虑过的替代方案

**把条目嵌入工作区浏览器。** 否决：工作区浏览器拥有会话分组、排序、搜索与拖拽——把部署专属的任务路由混入其中会耦合两个无关领域，并迫使每个工作区浏览器测试都知道业务条目。

**每个条目一个顶层 slot。** 否决：为单一概念分组新增七个外壳洞会让侧边栏约定膨胀，并使外壳拓扑依赖于部署的任务数量。用一个自包含占位方的单一 `sidebar.business` 洞可以让外壳在目录变更时保持稳定。

**在 ui-sidebar 内硬编码该分组。** 否决：侧边栏外壳只拥有列几何；业务内容属于占位方。内置占位方会破坏外壳的分离性，并使部署在不 fork 外壳的情况下无法替换或移除该分组。

**跨重载持久化展开与选择。** 否决：持久化选择需要在持久边界根据实时目录校验恢复的 id，而目录是静态源码——持久状态与变更后的目录之间的不一致需要为零当前消费者编写迁移逻辑。展开在重载时重置；持久化随消费者一起到来。

## 后果

侧边栏外壳增加一个可选的区域席位；没有业务条目的部署不注册占位方，区域在没有该分区的情况下渲染；由于占位方位于工作区扫描范围之外，生成的 slot 目录将该席位记录为未占用。插件部署到 Web profile 的 `node_modules` 并通过 profile 的补丁层注册；`apps/desktop/scripts/dev.ts` 会在 IM 插件旁重建并回拷它，家目录 `cordis.patch.yml` 的 `disabled` 行按机器停用它。store 在侧边栏折叠后存活，但在页面重载时不存活；接入消费者需要通过同一个声明句柄读取 store。条目目录是源码静态的：添加、删除或重新排序条目需要编辑插件的 `src/client/entries.ts` 并重新构建。
